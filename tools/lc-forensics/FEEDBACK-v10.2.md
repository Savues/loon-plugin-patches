## 二、三项修复验证

### ① `{}` 响应不再误判为 `.bin` ✅

**旧版问题**
```
reject_dict 拦截后返回 2 字节 {}，mime 为空 → 落到 bin 分支
实测 6 个：ads/resource / askdiandian / inspiration 等
```

**新版表现**
```
v10.2 生成的 366 个文件中，{} 存成 bin 的数量：0 个
```

**验证方法**（重要）：必须按时间戳分离新旧文件，因为 `lcf-resp` 目录不清空：

```bash
CUT=$(date -d '2026-10-27 03:20:00' +%s)   # 本次启动时间
ls lcf-resp | while read f; do
  [ $(stat -c %Y "lcf-resp/$f") -ge $CUT ] && echo "$f"
done
```

**我第一次检查时差点误判**：看到 6 个 `{}` 存成 bin 以为没修好，
核对时间戳发现是 v10.1 的旧文件（03:16-03:17 vs v10.2 的 03:25+）。

### ② HEIC 识别 ✅ 新增

| 项 | v10.1 | v10.2 |
|---|---:|---:|
| `.heic` 文件 | 0 | **25** |
| 存成 `.bin` 的 HEIC | 6 | **2**（变体 `rvic`） |

**magic bytes 对照**

```
正确识别：00 00 00 1c 66 74 79 70 68 65 69 63  → "....ftypheic"
仍漏判：  00 00 00 1c 66 74 79 70 72 76 69 63  → "....ftyp rvic"
```

`rvic` 是 **HEIF 的另一个品牌变体**（不是 heic）。

**建议**（成本极低）：
```c
// 不要枚举 brand，直接判 ftyp
if (len >= 12 && memcmp(buf + 4, "ftyp", 4) == 0) type = "heic";
```

理由：HEIF 家族已知品牌有 `heic` / `heix` / `mif1` / `rvic` / `avif`…
枚举永远会漏，判 `ftyp` 容器标记一劳永逸。

## 四、使用体验观察

### 1. index.jsonl 是追加式的 ⚠️ 需要注意

```
v10.2 运行后：531 行
  ├─ v10.1 的 161 行（指向 03:16 的文件）
  └─ v10.2 的 370 行（指向 03:25 的文件）
```

**优点**：历史记录不丢，全部指向真实存在的文件（无悬空记录）。

**使用注意**：跨版本分析时要按文件时间戳或 taskkey 区分批次。
例如我想查「v10.2 下 ads/resource 的响应」，直接用 index 会先命中 v10.1 的旧记录：

```
[ads/resource] 200 2B 53-59041880-200.bin   ← 这是 v10.1 的文件
```

**建议（可选）**：
- 方案 A：index.jsonl 每条加 `session` 字段（启动时间戳或 pid）
- 方案 B：每次启动生成 `index-<UTC>.jsonl`，另留 `index-latest.jsonl`
- 方案 C：保持现状，文档说明需按时间过滤

**我的倾向**：方案 A 最简单，加一个 `pid` 字段就行（日志里已有 pid）。

## 六、对未来版本的期望

| 优先级 | 期望 | 理由 |
|---|---|---|
| **P1** | `ftyp` 通用判断替代 brand 白名单 | 当前漏 `rvic`，HEIF 家族品牌很多，枚举不完 |

| **P3** | preview 支持 JSON 结构摘要 | 505 字符对深层嵌套仍不够 |

```bash
CUT=$(date -d '<本次启动时间>' +%s)
```
